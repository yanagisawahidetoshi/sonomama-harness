# ADR-0002: ユーザー登録をCS起点の招待制とする

- 状態: Proposed
- 日付: 2026-10-29
- 判断者: 未定
- 関連Issue: #110
- 関連SBI: なし

この文書は提案の段階にある。AIは、ここに書いた方針を決まったものとして実装や提案の根拠にしない。
Option A / Option Bのどちらを採るかも含め、人が判断してから状態を`Accepted`に変える。

## 背景

SONOMAMAでは、受講生・講師・講師リーダー・MG・CS・運営のすべてのロールについて、CSがユーザーを登録する運用を想定している。
現行の要件では、CSがIDとパスワードを発行し、ユーザーが初回ログイン時にパスワードを変更する。この方式では、CSが他人のパスワードを知ることになる。CSが認証情報を扱わない方式も含めて見直したい。

インフラはAWS、認証基盤はAmazon Cognito（User Pool）を使う（[ADR-0007](0007-aws-and-cognito.md)で決定済み）。
このADRでは、Cognitoの上で登録と招待の流れをどう組むかを決める。

## 判断ドライバー

- CSが他人のパスワードを知らずに済むこと
- 登録できる人を、CSが認めた人に限ること
- Cognitoの標準機能で実現でき、独自実装を増やしすぎないこと
- CSと利用者の手間が増えすぎないこと

## 選択肢

パスワードレス認証（Email OTP、Passkeyなど）は比較に含めない。認証の方式そのものを見直す場合は、別のADRで扱う。

### Option A: 認証基盤が一時パスワードを発行し、初回ログイン後に本人が変更する

CSがメールアドレスを登録すると、認証基盤が一時パスワードを作り、ユーザーへ送る。ユーザーは一時パスワードでログインしてから、自分のパスワードに変える。

Cognitoでは、`AdminCreateUser`の標準動作がこの流れになる。作られたユーザーは`FORCE_CHANGE_PASSWORD`の状態になり、初回ログインでパスワードの変更を求められる。一時パスワードの有効期限はUser Poolの設定（`TemporaryPasswordValidityDays`）で決め、再送は`MessageAction=RESEND`で行う。

### Option B: CSはメールアドレスだけを登録し、本人が初回パスワードを設定する

CSがメールアドレスを登録すると、そのユーザーへ招待メールが届く。ユーザーは招待メールから初回パスワードを設定して、利用を始める。

Cognitoには、管理者が作ったユーザーに招待URLからパスワードを設定させる標準機能がない。`AdminCreateUser`で招待メールを抑止し（`MessageAction=SUPPRESS`）、招待URLの発行・検証とパスワード設定をSONOMAMA Backend側で作る必要がある。

### 比較

| 観点 | Option A | Option B |
| --- | --- | --- |
| ユーザーに届くもの | 一時パスワード | パスワードを設定するための招待URL |
| 利用開始までの手順 | 一時パスワードでログインしてから変更する | 招待URLからパスワードを設定する |
| 招待の期限切れ・再送 | 一時パスワードの期限と再発行を決める必要がある | 招待URLの期限と再送を決める必要がある |
| 現行要件との差 | パスワードを発行するのがCSから認証基盤に変わる | 初回ログインの流れが変わる |
| Cognitoでの実現 | 標準機能で実現できる | 招待URLとパスワード設定を独自に実装する |

## 決定

未決定。現時点の提案は次のとおり。

- ユーザーが自分で自由にアカウントを作る自己サインアップは提供しない。
- すべてのロールについて、CSの登録を起点にする。
- CSが最初に登録する識別情報は、メールアドレスとする。
- 登録したユーザーには、メールで利用開始を案内する。
- パスワードなどの認証情報はCognitoが管理する。SONOMAMAのアプリケーションDBには保存しない。
- SONOMAMA固有のロール、状態、プロフィール、担当関係などの業務情報は、アプリケーション側で管理する。

## 未決事項

- Option AとOption Bのどちらを採るか
- 招待メールを送るのはCognitoか、SONOMAMA Backendか（Option Bを採る場合はBackendになる）
- 招待URLと招待状態の有効期限
- 招待を再送するときの仕様

## 認証基盤とSONOMAMA Backendの責務分担

| 担当 | 扱うもの |
| --- | --- |
| 認証基盤 | パスワードなどの認証情報、ログイン、パスワードの設定と再設定 |
| SONOMAMA Backend | ロール、ユーザー状態、プロフィール、担当関係、CSによる登録操作の受付 |

2つは、Cognitoが発行するユーザーの識別子（`sub`）で結びつける。Cognitoの呼び出しはSONOMAMA Backendの中の1か所にまとめ、業務ロジックからCognitoのAPIやSDKを直接呼ばない。

## 想定ユーザーフロー

Option Bの場合の流れを示す。

1. CSが管理画面で、ユーザーのメールアドレスとロールを登録する。
2. SONOMAMA Backendが、アプリケーション側のユーザーと認証基盤のユーザーを作り、紐付ける。作る順序と失敗したときの扱いは、設計文書で決める。
3. ユーザーに招待メールが届く。
4. ユーザーが招待メールから初回パスワードを設定し、ログインする。
5. SONOMAMA Backendが、そのユーザーを利用中にする。

Option Aでは、3と4が「一時パスワードを受け取ってログインし、パスワードを変更する」に変わる。

## ユーザー状態

| 状態 | 意味 |
| --- | --- |
| 招待中 | CSが登録したが、本人がまだ利用を始めていない |
| 利用中 | 本人が自分のパスワードを設定し、ログインした |
| 招待期限切れ | 有効期限までに利用を始めなかった。有効期限を設ける場合だけ使う |

退会や利用停止は、このADRでは扱わない。

## 影響

### Positive

- 登録できる人がCSの認めた人に限られる。
- パスワードがアプリケーションDBに入らないため、漏えい時の影響範囲が狭くなる。
- どちらの案でも、CSは他人のパスワードを知らずに済む。

### Negative / Trade-offs

- CSが登録するまで、ユーザーは利用を始められない。
- 招待の期限切れや再送への対応が、CSの運用に加わる。
- 認証基盤とアプリケーションDBの2か所にユーザーがいるため、両者の状態がずれないようにする必要がある。

## 実装・運用への影響

- 自己サインアップの画面とAPIは作らない。
- アプリケーションDBのユーザー情報に、パスワードやそのハッシュを持たせない。
- 管理画面に、CSがユーザーを登録する画面が必要になる。招待の再送と状態の確認も、仕様が決まれば必要になる。
- 認証とロールモデルに関わる実装になるため、SEC-AUTH-001とSEC-ROLE-001の対象になる（[authorization.md](../security/authorization.md)）。

## 検証方法

- 自己サインアップのAPIが存在しないことを、APIのテストで確かめる。
- アプリケーションDBのスキーマに、パスワードやそのハッシュの列がないことを確かめる。
- CSの登録から本人のログインまでの流れを、Cognito User Poolの上で通しで確かめる。

## 再検討条件

- 自己サインアップを求める業務要件が出たとき
- パスワードレス認証への切り替えを検討するとき
- Cognitoでは、この流れを実現できないと分かったとき
